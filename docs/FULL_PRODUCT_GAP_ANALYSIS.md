# PataFundi Full Product Gap Analysis

**Source of truth:** `Evian1k/Patafundi-9bhsw1` (the audit snapshot identified branch `fix/monorepo-mobile-auth-and-build`, commit `a5715eb`, with PR #7 open).
**Evidence used:** all 13 retained read-only domain reviews (`/home/ubuntu/.manus-jobs/0e1434cb81a7_a0/output.txt` through `_a12/output.txt`), `/tmp/pf-audit/Patafundi-9bhsw1/docs/MOBILE_APP_AUDIT_HANDOVER.md`, and the declared master prompt `/home/ubuntu/upload/pasted_content_2.txt`.
**Reducer constraints:** no application code was edited; no configured database was accessed, migrated, seeded, reset, or written; no deployment, commit, or push was performed. This document is a synthesis of the supplied reviews, not a new runtime certification.

## 1. Executive summary

**Judgment: PataFundi is not production-ready.** The repository is a substantial monorepo with a real Express/PostgreSQL backend, separate native customer and Fundi Expo apps, a web application, migrations, authorization primitives, private-storage abstractions, and meaningful backend regression coverage. The prior handover records **132 backend tests passed and 5 backend E2E tests passed against disposable PGlite**, plus web typecheck/build/lint and Expo TypeScript/Android/iOS JavaScript-export checks. Those results are useful evidence for the tested slices, but they do not establish the complete master-prompt product, production integrations, or release acceptance.

The most serious blockers are not cosmetic:

- **Shared truth is fractured.** Service categories remain hardcoded and divergent in web/mobile while the database-managed country catalog has no demonstrated seed/admin lifecycle. Role and state definitions are split across user roles, company memberships, legacy admin guards, direct status writes, and client-specific API shapes.
- **Transactional integrity is unsafe.** The normal OTP completion path sets `customer_confirmed_completion` and then calls settlement code that only accepts `completed`; generic status routes and many direct writes can bypass the central state machine, OTP, payment, or offer checks. Quote revisions, timelines, and settlement are not consistently atomic.
- **Money movement is not provider-confirmed.** The M-Pesa internal path has useful validation and replay protection, but ledger migrations conflict, refunds can fail or over-debit on partial refunds, payout completion can be marked locally without a provider transfer, and Stripe/subscription/reconciliation behavior is incomplete or unverified.
- **Authorization and privacy have high-impact gaps.** Sensitive legacy routes accept `admin` rather than named permissions; company/profile eligibility differs between directory and direct profile; exact location is disclosed too early; staff projections can expose sensitive identifiers; MFA-required flags are not enforced; and browser token/session design needs repair.
- **Customer, Fundi, company, staff, and mobile journeys are not end-to-end.** Mobile wallet/payout/status/availability contracts disagree with backend responses; Fundi offer discovery and work progression are incomplete; company application documents, scheduling, qualification and subscription tenancy are partial; support and trust/safety are not full workspaces; and photo upload can report success after failure.
- **Operational acceptance is open.** There is no browser/mobile E2E or accessibility harness, no verified staging/live deployment, no production-grade backup restore, and no live provider, device, signed-release, or store verification. Queue recovery, retention/deletion, pagination, realtime fan-out, and migration/documentation consistency also require work.

The repository should therefore be treated as a **strong implementation baseline requiring a dependency-ordered hardening and completion program**, not as a deployable marketplace. No feature below is called complete unless the supplied evidence supports it.

## 3. Critical security and data-integrity gaps

Priority reflects exploitability and the possibility of corrupting money, identity, privacy, or platform state.

### P0 — Must be closed before any production data or real-money launch

1. **Unsafe bootstrap, seed, reset and known credentials.** Remove automatic non-production seeding from `backend/src/server.js`; require an explicit disposable-environment marker and allowlisted database identity for `ensure-dev-db.js`, `seed-takeover.js`, `cleanup-demo-data.js`, and `db-reset.js`. Rotate/remove published demo credentials and enforce a singleton/equivalent owner invariant. Add staging-safety tests that prove no remote connection, DDL, seed or deletion occurs under unset/development/staging defaults.
2. **State-machine and settlement bypass.** Disable or make read-only generic status PATCH routes; route every status mutation through one transactional service with actor, current-state, offer, quote, OTP, trusted-payment, and optimistic-concurrency checks. Repair `customer_confirmed_completion` → settlement sequencing and make ledger/payout/review state atomic and honest.
3. **Canonical ledger/provider truth.** Resolve the migration 005/029 `revenue_ledger` contract conflict before applying to a real database. Add exactly-once source/event keys and balance invariants. Do not mark payouts/refunds complete without provider confirmation; implement M-Pesa reversal/B2C or supported transfer and Stripe event/refund validation, retry and reconciliation.
4. **Sensitive authorization and tenant boundaries.** Replace legacy `requireRole('admin')` with named permissions/object checks; protect super-admin targets; enforce active membership everywhere; require technician role/qualification and offer ownership; prevent owner promotion; make company subscriptions explicitly company-bound. Apply the same verified/active/subscription/service-area rules to public directory and profile.
5. **MFA/session and secret handling.** Add the missing MFA state columns or remove stale writes, enforce required 2FA before issuing sessions, repair encrypted recovery storage and fail closed without `ENCRYPTION_KEY`. Use a reviewed same-origin httpOnly-cookie/CSRF design or equivalent, avoid browser-local long-lived tokens, and test refresh rotation/replay/logout/role revocation.
6. **Private location and file handling.** Return only coarse location before assignment/acceptance; rate-limit OTP resend and do not return/store plaintext OTPs. Implement job-photo/profile/support uploads with ownership, expiring signed reads, access logs and object cleanup; remove arbitrary support attachment URLs and harden local fallback or disable it outside isolated development.

### P1 — Must be closed before a broad beta or operational rollout

7. **One shared contract/state/catalog foundation.** Define typed request/response/error schemas for backend, web, both mobile apps and `packages/shared`; canonicalize user/company roles, job/quote/payment states, event/timeline semantics and service aliases. Make the catalog database-driven, country-scoped, authorized/audited, seeded safely, and consumable by every client with explicit free-text/unlisted requests.
8. **Notification and safety truthfulness.** Implement a transactional notification outbox with event/entity idempotency, channel intent, delivery result, retry/dead-letter, recipient scope and assignment/resolution. Persist every safety report, create a human-review case, separate automated signals from adjudicated enforcement, and protect audit records against UPDATE as well as DELETE.
9. **Data lifecycle and bounded reads.** Unify direct delete and GDPR anonymization/session revocation; define legal holds/retention for all PII-bearing tables and objects, including provider callbacks, files, locations, chat, disputes and audit/fraud data. Add cursor pagination/projections/indexes for jobs, admin lists and Fundi search.
10. **Background and realtime reliability.** Add queue leases/heartbeats/reaping, dead-letter/re-drive, readiness/metrics and non-swallowed failures. Complete event names/rooms/consumers and per-handler socket cleanup; ensure admin/staff room fan-out is authorized and tested.

### P2 — Required for full acceptance and scale

11. **International and financial reporting correctness.** Remove silent Kenya/original-amount currency fallbacks; gate country activation on payment/tax/service/provider configuration; model partial refunds, subscriptions, renewals/grace/cancellation, chargebacks and authoritative GMV/take-rate/MRR/payout reporting.
12. **Accessibility, SEO and product quality.** Add labels/roles/focus/keyboard semantics, native accessibility labels, reduced-motion parity, per-route metadata/canonical/JSON-LD/sitemap, and automated axe/Lighthouse/device checks.
13. **Recovery and operational evidence.** Replace local/manual backup with scheduled encrypted durable off-cloud backups covering database and objects; test restore, integrity, RPO/RTO and rollback against isolated infrastructure.

## 4. Dependency-aware implementation phases

The order below is intentionally dependency-aware. Do not begin broad UI parity or release work on top of divergent contracts, unsafe state writes, or an untrusted catalog.

### Phase 1 — Universal contracts, state, authentication, storage boundaries, and catalog

1. Freeze the authoritative role registry and permission matrix, including company membership roles and `ops_manager`; replace legacy admin guards with permission/object checks. Define shared schemas for auth/MFA, users, roles, errors, jobs, quotes, payments, locations, notifications, files and pagination.
2. Canonicalize job/quote/payment/refund/subscription states and actors. Route all writes through transaction-aware services and add timeline/event contracts before adding new screens.
3. Finish auth hardening: required MFA state/schema, encrypted recovery behavior, browser refresh/CSRF/session design, refresh replay/logout/role-revocation tests, owner bootstrap invariant, and removal of known-credential auto-seeding.
4. Establish a safe storage contract: private object keys, ownership, expiring signed reads, access logs, upload/delete/retention semantics, local-development isolation, and no caller-supplied attachment URLs.
5. Build one normalized, country-aware service catalog with alias validation, authorized CRUD/audit, safe seed data, country enablement and explicit inactive/unlisted/free-text handling. Migrate web, customer mobile, Fundi mobile, company services and matching away from static lists without overwriting existing marketplace data.
6. Add disposable migration/contract tests for the final schema, ledger prerequisites, owner/MFA columns, catalog parity, country-service visibility, verification ownership, and role/permission matrix. Do not point these tests at configured data.
